## 指示書からの逸脱・判断 (正直に)

1. **タスク1 system_status の粒度**: `system_status` の PK は `(check_name, check_date)` のため「戦略ごとに1行」は不可能。同日の複数戦略は `signal_eval_failure` 1行の `detail_json.strategies` に merge して upsert。「同日同戦略は1回」はプロセス内 set + 行内 strategies の存在チェックで担保 (再起動・複数 worker でも重複記録なし)。
2. **タスク2 maintenance「最終判定」の解釈**: 明示の tick が無いため「次の 10 分 tick が 07:00 以降になる tick (= 06:50)」を最終判定とした。また指示書は `degraded` のみ言及だが、最終 tick でフェーズを実行して失敗した場合の戻り値は `waiting` (incomplete_phases なし) のため、`noop`/`ready` 以外は task_runs から未完フェーズを再判定して非0にした (「未完フェーズあり=最終失敗」の趣旨に合わせた拡張)。ロック競合 (`noop`) は誤報防止のため 0 のまま。
3. **タスク3 クールダウンの起点**: メール送信「試行」時点で開始 (送信バックエンド故障時の連投も防ぐ)。クールダウン状態が読めない場合は可視性優先で送信する。
4. **タスク5 実装位置**: `record_cron_run` (`src/db/cron_run_log.py`) は status を running/success/failure に限定しており、同ファイルは本作業の編集許可外。そのためスクリプト内に `_record_cron_skip` を新設。さらに旧コードには「スキップ時に並行実行中の `running` 行を success で上書き→多重実行検知 (`_exhibition_refresh_recently_running`) が壊れる」問題もあったため、`running` 行は上書きしないガード付き upsert とした (success_at は決して書かない)。
5. **既存テスト更新の要否**: bootstrap の `test_expected_source_waiting_is_a_successful_scheduler_tick` は run_tick を mock しており `alert_status` を含まない (=None) ため新セマンティクスでもそのまま green (「リトライ残ありの waiting は 0」の意図と整合)。**更新不要だった**。「07:30 未解決=非0」は `tests/test_cron_exit_codes.py` 側で新規に検証。
6. 読み手側の `skipped` 対応: grep の結果、`task_runs.status` の読者は app.py admin (`_format_runtime_status` は未知値を素通し表示 / `_compose_admin_status` は warning 扱い)、`task_success_exists` (success のみ判定)、overlap 検知 (running のみ判定) で、いずれも `skipped` で壊れない。admin の展示後更新行の note に skipped 表示の説明を追記。
