## 1. 事故率の定義を既存ROIに合わせる（最優先）

### 1-1. 既存の定義を調査して正確に踏襲する
- `src/web/app.py` の事故率参照ロジック（`racer_accident_period_stats` を
  `source_kind` / `rule_version` / 審査期間 / レース日前の最新行 で引く部分）を**読んで**、
  同じ選択規則を `asof_builder` に実装する。**推測禁止・コードを正とする。**
- 既存が `COALESCE(..., 0)` で欠損を0扱いしている場合、**その挙動も踏襲する**
  （ユーザー決定「既存ROIを正」に従う）。ただし後述のとおり欠損は別列で識別できるようにする。

### 1-2. as-of テーブルの列変更（schema_version=5）
- 既存の `bN_accident_rate`（過去365日の事故件数率）は **`bN_accident_rate_365d` に改名**して残す
  （比較・検証用。過去の保存手法の互換のため後述のマイグレーションを行う）。
- **新規 `bN_accident_rate` = 既存ROI互換の事故率**（審査期の事故率）。
- **新規 `bN_accident_points`** = 既存ROI互換の事故点（既存が事故点で判定している手法があるため）。
- **新規 `bN_accident_source`** = 値の由来（'period' = 審査期行あり / 'missing_zero' = 欠損を0扱い）。
  これにより「本当に0の選手」と「データが無くて0にした選手」を区別できる。
- 各列とも as-of 規約を厳守（レース日**前**の最新行のみ参照。当日以降のデータ禁止）。

### 1-3. 検索条件
- `accident_rate`: 既存ROI互換の事故率（min/max）
- `accident_points`: 事故点（min/max）
- `accident_rate_365d`: 従来の365日事故件数率（min/max）— 別名で併存させる
- 画面のラベルを明確に区別する:
  - 「事故率（審査期・既存ROI互換）」
  - 「事故点（審査期）」
  - 「事故率（過去365日・参考）」
- 保存済み手法の互換: 旧 `accident_rate`（365日定義）で保存された手法が既にある場合、
  **意味が変わってしまうため**、マイグレーション方針を決めて実装し結果レポートに明記すること。
  推奨: 保存時の schema を見て旧定義なら `accident_rate_365d` に読み替える。
  （現在の保存済み手法は検証用の少数のみなので、単純な読み替えで良い）

### 1-4. クロスチェックでの確認（必須）
- Step 10 のスクリプト `scripts/crosscheck_roi_strategies.py` を**再実行**し、
  事故率が原因で不一致だった3手法
  （`tamagawa_13_acc2n30_m3_40_exa`, `kojima_12_acc3_m3_n23_exa`, `edogawa_13_acc2_n23_m3_exa`）が

## 3. 確定オッズ（人気帯の分析用）

### 3-1. 設計方針（重要）
**買い目の確定オッズで絞り込む形は実装しない**（結果が来たレースだけが残り、
的中率100%・回収率異常膨張の未来情報バイアスになるため）。
代わりに**レース全体の荒れ具合**を表す指標として提供する:

- `final_odds_favorite`: そのレースの**3連単・最低オッズ（＝1番人気の確定オッズ）**の帯。
  全レースについて必ず1つ存在するため、絞り込んでも偏りが生じない。
- 条件例: `"final_odds_favorite": {"min": 5.0, "max": 15.0}`

### 3-2. データ
- `asof_race_features` に **`final_odds_favorite` REAL** を追加（schema v5）。
  算出元: `race_payouts` ではなく、**確定オッズ（odds_trifecta の final スナップショット）**があればそれ、
  無ければ**当該レースの3連単払戻÷100**は使えない（払戻は当たった組のみ）ため、
  **T-5min の最低オッズ**を使うか、算出不能なら NULL。
  → **実装前に調査**: 全レースの「1番人気の確定オッズ」を復元できるデータがあるかを確認し、
  無い場合は `t5_odds_favorite`（T-5minの最低オッズ）として提供し、UIラベルもそれに合わせる。
  調査結果と採用した定義を結果レポートに明記すること。**データが無いものを捏造しない。**
- NULL のレースは条件使用時に condition_null 除外。

### 3-3. 画面の警告（必須）
- この条件の近くに常時表示:
  「レース全体の人気度（1番人気のオッズ帯）で絞り込みます。**締切前には確定しない情報**のため、
   傾向分析用です。当日の照合では未確定として扱われます。」
- 照合（strategies）では当日確定（⏱）扱いで pending 分類。

## 4. 風向き

### 4-1. 会場ごとのスタンド方位マスタ（新規）
- `master/stadium_orientations.json` を新規作成。各会場（1〜24）について
  **「1マークから2マークへ向かう直線（＝ホームストレッチの進行方向）の方位角（度）」**を定義する。
- 値は公開情報（各会場の水面レイアウト）に基づく。**推測で埋めず、確度が低い会場は `null`** とし、
  null の会場では風向き条件を「判定不能（condition_null 除外）」とする。
  どの会場を null にしたかを結果レポートに列挙すること。
- 各エントリに出典または根拠のコメントを残す。

### 4-2. 導出ロジック（asof_builder, schema v5）
- `wind_dir_raw`（16方位番号、既存列）と会場方位から `wind_dir` を導出:
  - 風向の方位角と、艇の進行方向の方位角の**相対角 θ** を計算
  - θ が ±45度以内 → **向かい風**（艇が進む方向から吹いてくる）
  - θ が 135〜180度 → **追い風**
  - それ以外 → **横風**（左右の区別は、相対角の符号で `横風(右)` / `横風(左)`）
  - **判定規約（向かい風/追い風の定義がどちらの符号か）を docstring に明記**し、テストで固定する
- 風速が0（無風）または `wind_dir_raw` が無風コード（17）の場合は `wind_dir='無風'`
- 会場方位が null の会場は `wind_dir = NULL`

### 4-3. 検索条件・画面
- `wind_dir`: `["追い風", "向かい風"]` のような配列（OR）。
- 画面の風向きセレクトを有効化（現在「指定なし（未対応）」になっている箇所を実装）。
- ⏱バッジ（当日確定）を維持。
