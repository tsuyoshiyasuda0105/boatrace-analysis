# 勝ち筋サーチ 全項目網羅バグチェック 仕様書

作成: 2026-08-16 リン（Claude Code）/ 発注先: Codex
目的: ユーザー指示による網羅的バグ出し。**全ての検索条件項目を1つずつ設定して検索を実行し、
結果が正しく出力されるか（エラー・空・異常値が出ないか）を確認する。**
バグ発見のみ。修正はしない（見つかったら翌日対応）。

## ユーザー指定のチェック方針（厳守）

1. **買い目は必ず何か選択する**（単勝/2連単/3連単のいずれか）。買い目なしの検索はしない。
2. **各条件項目を1か所ずつ設定して検索**を行い、結果が出力されるか確認する。
3. **全ての選択肢の通りを検索**し、データが出力されるかチェックする
   （例: 会場なら24会場すべて、級別ならA1/A2/B1/B2すべて、天候・風向き・潮の全選択肢、
   艇別条件の各比較演算子、艇間比較の各指標 等）。

## 絶対的な制約（違反禁止）

1. **バグ修正禁止**。プロダクトコードを一切変更しない。
   作ってよいのは検証スクリプトとバグ報告のみ。
2. DB は**読み取り専用**（`data/kachisuji_search.db`）。`data/boatrace.db` には接続しない。
   DB書込み・DDL禁止。手法保存を伴うテストは一時的な strategies DB を使い、
   実運用の手法DBを汚さない。
3. サーバーはテスト内で subprocess 起動 → 終了時に確実に kill（ポート8090。8080の本番運用と分離）。
   起動しっぱなしにしない。
4. ネットワーク・スケジューラ・デプロイ・push 禁止。
5. コミットは main へのローカルコミット1つ。
   メッセージ: `Add exhaustive per-field search smoke check (kachisuji round 2)`。

## チェック内容（全項目を機械的に網羅）

各項目について「買い目を固定（例: 単勝1）＋その項目だけを1値設定」で検索APIを叩き、
レスポンスを検査する。基準は下記「合否判定」。

### A. レース条件
- **会場**: 1〜24 の全24会場
- **買い目**: 単勝(1〜6の代表)、2連単(1-2等の代表)、3連単(1-2-3等の代表)。
  さらに各券種で着順の艇番を変えたパターンをいくつか
- **レース番号範囲**: 1R〜12R の代表的な範囲指定
- **天候**: 晴 / 曇 / 雨 の各単一選択
- **風向き**: 追い風 / 向かい風 / 横風(左) / 横風(右) の各単一
- **風の強さ**: 各段階
- **潮**: 満潮前後 / 干潮前後 / 上げ潮 / 下げ潮 の各単一

### B. 番組・市場条件
- **性別構成**: 男性のみ / 女性選手あり
- **級別構成**: A1単騎 / 1号艇A1 / A1が2人以上（実装されている全選択肢）
- **開催日程**: 初日 / 中日 / 最終日
- **時間帯**: モーニング / デイ / ナイター

### C. 艇別条件（1〜6号艇それぞれ、代表として1号艇＋数艇で）
- **級別**: A1 / A2 / B1 / B2 の各単一 ＋ 複数選択の代表
- **平均ST**: 以上 / 以下 の各方向で代表値
- **全国勝率・当地勝率**: 以上 / 以下
- **全国2連対率・当地2連対率**: 以上 / 以下
- **モーター2連対率**: 以上 / 以下
- **展示順位**: 範囲指定
- **展示タイム会場平均比**: 速い / 遅い
- **展示ST**: 以上 / 以下
- **決まり手**: 逃げ/差し/まくり/まくり差し/抜き/恵まれ の各 ＋ 勝率閾値
- **事故率（3種: 本日判定用 / 検証用 / 365日）**: 以上 / 以下
- **事故点・事故件数**: 以上 / 以下
- **年齢**: 以上 / 以下

### D. 艇間比較
- 各指標（motor_rate2 / avg_st / ex_time / ex_st / national_rate / local_rate /
  national_rate2 / age 等、実装されている全指標）で ge / le の両方
- margin あり / なし（0）

### E. 買い目そのもの
- 単勝: first を 1〜6 の全通り
- 2連単: first-second の代表パターン
- 3連単: first-second-third の代表パターン

## 合否判定

各検索リクエストについて:
- **PASS**: HTTP 200 で、レスポンスが正しい構造（n / hits / roi / yearly / monthly / excluded 等）を持つ。
  n=0 でも「正しく0件」ならエラーではない（該当レースが無い条件はあり得る）。
- **FAIL(error)**: HTTP 400/500、例外、レスポンス構造の欠落、JSON パース不能
- **FAIL(anomaly)**: 明らかな異常値。例:
  - roi が負、または極端（例 >100000%）
  - hits > n（的中が母数を超える）
  - yearly/monthly の n 合計が全体 n と不一致
  - excluded の内訳合計がおかしい
  - condition_null が全件（＝その条件が全レースで判定不能 ＝ Step 19 の逃げ率0件のような
    「事実上使えない項目」の疑い）→ **これは要注意として別途フラグ**

- **注意フラグ（バグではないが報告）**:
  - ある選択肢が「常に n=0」になる（データが無い/条件が実質機能していない）
  - データ期間が限られる項目（展示系2024/11〜等）で古い期間が全除外される（仕様どおりだが列挙）
