# 作業指示書: DB 一時障害でエラー画面を出さない (Codex CLI 用)

作成: 2026-08-15 / 発注者: リッキー / 検品: リン (Claude)
リポジトリ: `C:\boat_project\boatrace-analysis` (正本のみ)
現行 main: **716 passed** / 本番 revision `f2ee23a`。

## 背景 (2026-08-15 夕方の実障害・再発)

会員が画面を開くと、こんなエラーページが出た:

> 予測エラー: DB 接続エラー。30秒後に再度アクセスしてください。

出所は `src/web/app.py` の**グローバル 500 ハンドラ** (`handle_500`, ~6088行)。
`race.html` を `stadium_name="Error"`, `race_number=0` で描画するため、画面には
「OR Error」「0: ERROR」という**意味不明な見た目**になる。

根本の連鎖:
1. DB 接続プール (psycopg_pool) が一時的に枯渇 or 応答遅延
2. `PoolTimeout: couldn't get a connection after 5.00 sec` が送出される
3. どのルートでも例外がそのまま上がり **500**
4. 500 ハンドラが上記のエラーページを出す

**問題の本質**: このアプリは**キャッシュ済みの表示内容を大量に持っている**のに、
DB が一瞬詰まっただけで**それを使わずエラーを出す**。販売するアプリとして
「たまに真っ赤なエラーが出る」は許容できない。

## ゴール

**DB が一時的に使えなくても、会員にエラー画面を見せない。**
古い内容でよいので表示する。それも無ければ、穏当な「準備中/再読込」案内を出す。

## 絶対ルール

1. **origin/main へ push 禁止** (ローカル main まで)。
2. ROI 戦略ロジック・予測ロジック・DB スキーマ・render.yaml は変更しない。
3. **データを捏造しない**。古いキャッシュを出すときは「最新ではない可能性」が
   分かる控えめな表示を添える (大げさな警告バナーにはしない)。
4. `.venv/Scripts/python.exe -m pytest tests/ -q` — **716 passed を割らない**。
5. 作業ログ `reports/graceful_db_degradation_work_log_20260815.md`。コミット2〜3個。

## やること

### 1. DB 接続の一時失敗を「再試行」する薄い層

`src/db/connection.py` の接続取得で `psycopg_pool.PoolTimeout` (および同等の
一時的接続エラー) が出たとき、**短い待機を挟んで1〜2回だけ再試行**する。
- 例: 0.2秒 → 0.5秒のバックオフで最大2回再試行 (合計待ち時間は数百ms程度に抑える)。
- **無限リトライ・長時間ブロックは禁止** (それ自体がワーカーを詰まらせる)。
- 恒久的なエラー (認証失敗・DB不存在等) は**再試行しない**で即座に上げる。
- 環境変数で回数/待機を調整できると望ましい (既存の `BOATRACE_DB_POOL_*` の流儀に合わせる)。

### 2. 主要ページで「DB が駄目なら古いキャッシュを出す」

対象は**会員が最初に触る画面**:
- `/races` (本日のレース一覧, ~6656行): 既に `_read_top_page_snapshot` を持つ。
  スナップショット取得や後続 DB 処理が接続エラーで失敗したら、
  **期限切れでもよいので直近のスナップショット/ページキャッシュを返す**。
- `/race/<race_id>` (レース詳細): 既に stale フォールバックと「準備中」ページがある。
  **接続エラー時も 500 にせず**、stale → 無ければ「準備中」ページ (200) に落とす。

実装は**共通ヘルパー1つ**にまとめ、各ルートに散らさないこと
(例: 「DB 依存の描画を試し、一時的 DB エラーなら stale を返す」ラッパー)。

### 3. 500 ハンドラの見た目を直す

どうしても最後まで失敗したときの `handle_500` を改善:
- `race.html` を `stadium_name="Error"` で流用するのをやめ、
  **専用の軽量テンプレート** (例: `error_temporary.html`) を用意する。
  「OR Error」「0: ERROR」のような意味不明な表示をなくす。
- 文言は穏当に (例:「ただいま混み合っています。数十秒後に自動で再読込します」)。
- **自動リロード** (meta refresh, 30秒) を入れる。
- **テンプレート描画で DB を引かない** (①の `race_preparing.html` と同じ方針。
  Flask のコンテキストプロセッサが DB を引く場合は、それを回避して描画する)。
- ステータスコードは 500 のままでよい (監視のため)。ただし**画面はエラーに見せない**。

### 4. 一時 DB エラーの可視化

一時的 DB エラーが起きた事実を、既存の仕組みで**軽く**記録する
(`system_status` の既存パターンを流用。**新テーブルは作らない**)。
記録はベストエフォートで、**失敗しても本流を止めない**。
これがないと「頻繁に起きている」ことを後から誰も証明できない。

## テスト (`tests/` に追加)

- PoolTimeout が1回起きても再試行で成功すればページが正常表示される。
- DB が完全に駄目なとき、`/races` が**古いスナップショットを 200 で返す**。
- DB が完全に駄目で stale も無いとき、**エラーに見えない案内ページ**が返る
  (「OR Error」表記が出ないこと)。
- レース詳細が接続エラー時に 500 のエラーページではなく stale/準備中を返す。
- 恒久エラー (認証失敗等) は再試行せず速やかに失敗する。
- 500 テンプレートが DB を引かない。
