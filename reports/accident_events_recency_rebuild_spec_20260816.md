# 事故データ（本番 boatrace.db）直近欠測の再構築 実装仕様書

作成: 2026-08-16 リン（Claude Code）/ 発注先: Codex
対象DB: **本番 `data/boatrace.db`**（Step13 の kachisuji_search.db とは別系統）
きっかけ: 外部照合サイト（interq.or.jp「2027年前期級別審査」2026-05-01〜08-15）とアプリの
事故率・事故点・出走数に系統的な差異を検出したため。

## 背景と目的

アプリの事故率／事故点／出走数が**実際より低め（甘め）に表示**されている。
上位200選手を外部サイトと機械照合した結果:

- 級別 200/200 一致・性別 200/200 一致・選手欠落0（**マスタは健全**）
- 事故点 合計: 参照 **1,465** → アプリ **845**（約58%しか計上できていない）
- 出走数 合計: 参照 **14,806** → アプリ **14,165**（−641）
- 参照では事故があるのにアプリが**事故点0**の選手が **70人**

## 確認済みの事実（調査根拠）

1. `racer_accident_events`（本番）の月次カバレッジに構造的欠落:
   - 2016〜**2025-06** 連続 → **2025-07〜2026-04 の10か月が完全空白** →
     2026-05・06 復活 → **2026-07 は 07-21 で停止** → **8月は0件**
2. 70人の「事故点0」は当期間で**イベントも `racer_accident_kraw_unmatched` も両方0件**。
   → **未マッチ（no_matching_entry 3,536行）は今回の主因ではない**。
      未マッチは最新でも 2026-06-19 止まりの歴史的バックフィル残渣で、別タスク。
3. 参照サイトで当該選手の F は **7/23・7/25・7/28・7/29 など07-21以降**に集中。
   → **直近の未取込が主因**。
4. 生データは揃っている:
   - `data/raw/results/` に **K260816.TXT まで展開済み**（8月分16ファイル確認）
   - `races` は 2026-08 = 2,604レース、`race_entries` は 2026-08 = 15,624行あり
   - 「事故点0」の選手も 07/22〜08/16 に出走登録済み（例: 細川4123=21, 深川3623=19）
   → **データは有るのに再構築処理が回っていないだけ**。
5. 根本原因（構造）:
   `scripts/pc_nightly_prepare.py` L79 が
   `rebuild_racer_accident_stats.py --local --from {today} --to {target_date}`
   と**当日〜翌日の増分のみ**を再構築。夜間ジョブ `BoatracePcNightlyPrepare` が
   07-21以降実効していない（CLAUDE.md「直近結果0」と符合）ため、以後の日が永久欠測。
6. ③FL=30 は優勝戦フライング（`racer_accident_point_rules`: FL base=20 / yusho=30）で
   **正規ルール。バグではない**。

## 検証用フィクスチャ（同梱済み）

`reports/accident_ref_2027maeki_interq_20260815.json`
- 外部サイトから取得した上位200選手の参照値（登番・氏名・級別・性別・勝率・

## ゴール（今回の主対象 = Phase A）

本番 `data/boatrace.db` の事故系テーブルを **2026-08-16 まで**再構築し、
外部サイトと**実質一致**する状態に戻す。

## 絶対的な制約（違反禁止）

1. **着手前に必ず `data/boatrace.db` をバックアップ**（例:
   `data/backups/boatrace.db.bak_20260816_accident_rebuild`）。後戻り用。
2. 本番DBへの書込みは **既存スクリプト経由のみ**:
   - `scripts/rebuild_racer_accident_stats.py`
   - `scripts/cache_racer_accident_rank_snapshot.py`
   スキーマ変更・DDLは不要（行わない）。他テーブルには触れない。
3. `data/raw/results/` は**読み取りのみ**。解凍が要る場合は一時展開し元ファイルを保持。
4. **ネットワークアクセス禁止**（外部サイト再取得は不要。フィクスチャで検証する）。
5. **タスクスケジューラを触らない・再有効化しない**。`install_all_tasks.ps1` /
   `startup_catchup.py` は実行禁止（CLAUDE.md 準拠）。デプロイ・push 禁止。
   Supabase 同期は行わない（`--skip-sync` 相当。ローカルSQLiteのみ）。
6. コード変更は原則不要。もし再構築/マッチングにバグを発見した場合のみ、
   最小限の修正＋対応テストを加え、根拠をレポートに明記。
7. 全期間・大規模な実行判断が要る場面は勝手に広げず、Phase B は**別途承認**を待つ。

## 作業手順（Phase A）

1. **バックアップ**（制約1）。
2. **現状スナップショット記録**: 再構築前の
   `SELECT substr(race_date,1,7),COUNT(*) FROM racer_accident_events GROUP BY 1`
   と、フィクスチャ照合の初期値（事故点合計・0人数）をレポートに控える。
3. **ドライラン**:
   `python scripts/rebuild_racer_accident_stats.py --local --from 2026-05-01 --to 2026-08-16 --dry-run`
   で対象件数・スキップ件数をプレビュー（黙って落とさない）。
4. **本実行（当期の穴埋め）**:
   `python scripts/rebuild_racer_accident_stats.py --local --from 2026-05-01 --to 2026-08-16`
   - 2026-05-01起点で当期（2027前期）を丸ごと再構築（冪等前提。重複が出ないこと）。
   - 07-22〜08-16 が新たに埋まることを確認。
5. **ランクスナップショット再生成**:
   `python scripts/cache_racer_accident_rank_snapshot.py --date 2026-08-16 --db-path data/boatrace.db`
6. **再照合スクリプト**（`scripts/` か一時スクリプトで可、恒久化は任意）:
   フィクスチャ `reports/accident_ref_2027maeki_interq_20260815.json` の200選手について、
   `racer_accident_rank_snapshots`(period_end='2026-08-16') と比較し、
   事故点合計・出走数合計・「事故点0なのに参照>0」の残存数を出力。
7. 結果を `docs/accident_events_recency_rebuild_result_20260816.md` に記載。

## 期待結果（許容差の考え方）

参照は 08-15 まで／アプリは 08-16 まで（1日多い）、優勝戦FLの扱い等で**完全一致にはならない**。
以下を「復旧」とみなす目安:

- 「事故点0なのに参照>0」の70人が **残り10人未満**に減る（0に近いほど良い）。
- 事故点合計がアプリ ≧ 参照×0.95（現状の845=58%から大幅改善。1日多い分アプリがやや多くても可）。
- 出走数合計の対参照差が **±150以内**（現状−641から改善）。
- 残差が出る選手は、参照のF/L日付が 08-16 より後、または優勝戦FL差など**説明可能な理由**を
  レポートに列挙（黙って許容しない）。
