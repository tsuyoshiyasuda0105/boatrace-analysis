# 作業指示書: 朝のページ生成がタイムアウトで全滅する問題の根治 (Codex CLI 用)

リポジトリ: `C:\boat_project\boatrace-analysis` (正本のみ)
現行 main: **811 passed**。

## 背景 (2026-08-16 朝の実障害・3日連続)

会員が朝アプリを開けなかった。原因は確定済み:

```
task_runs: render_maintenance_detail_v1 / 2026-08-16 / failure
detail: {"attempt_count": 3,
  "error": "TimeoutExpired: Command '[... 'scripts/prewarm_race_detail_tags.py',
            '--date', '2026-08-16']' timed out after 899.99 seconds"}
```

朝の時点のデータ状態:
- races 192 / predictions 1152 は **投入済み (正常)**
- **race_detail_page キャッシュ 0 件 / top_page_snapshot 0 件 / market_signals 0 件**

つまり**素材は揃っているのに、表示用ページが1枚も作られていない**。
`prewarm_race_detail_tags.py` が **900秒の上限を超え、3回試行してすべて時間切れ**。
タイムアウトすると **subprocess が kill され、その回の成果が全部無駄**になる。
8/14・8/15・8/16 と **3日連続**で同じ失敗をしている (今朝入れた自己修復も、
タイムアウト自体は救えなかった)。

## ゴール

**時間切れが起きても「作った分は残る」ようにし、朝までに必ずページが揃う**。
1回で全部やろうとして全滅する構造をやめる。

## 絶対ルール

1. **origin/main へ push 禁止** (ローカル main まで)。
2. ROI 戦略・予測ロジック・DB スキーマ・render.yaml (スケジュール/プラン) は変更しない。
3. `.venv/Scripts/python.exe -m pytest tests/ -q` — **811 passed を割らない**。
4. 作業ログ `reports/prewarm_timeout_fix_work_log_20260816.md`。コミット2〜3個。

## やること

### 1. prewarm を「時間予算内で刻む」方式にする

`scripts/prewarm_race_detail_tags.py` (および同じ問題を抱えるなら
`scripts/prewarm_race_detail_pages.py`) に **時間予算オプション**を追加する:

- `--budget-sec N` (仮): **N 秒経過したら、処理中のレースを完了させて正常終了 (exit 0)**。
  「途中まで終わった」ことを **成果として残す** (作った分のキャッシュは保存済み)。
  残件数を stdout / detail に出す。
- **未処理のレースを優先する**: 既にキャッシュがあるレースはスキップし、
  **無いものから処理**する。これにより次回起動が自然に続きから再開する
  (既存に skip 相当のロジックがあれば流用。無ければ追加)。
- **1レースごとにコミット/保存**すること (途中 kill されても直前までが残る)。
  現状が最後にまとめて書く実装なら、逐次保存に改める。

### 2. 呼び出し側を「予算内で複数回」に変える

`scripts/render_maintenance_scheduler.py` の detail フェーズ:
- 現在: `run_py([... prewarm_race_detail_tags.py ...], timeout=900)` で一発勝負。
- 変更後: **`--budget-sec` を渡し、subprocess のタイムアウトは予算より余裕を持たせる**
  (例: 予算 600 秒 / timeout 900 秒)。予算内で終わらなければ **正常終了して次のフェーズへ**進み、
  **残件は後続の tick / self-heal が引き継ぐ**。
- **時間切れ = フェーズ失敗、にしない**。残件があっても「部分成功」として記録し、
  pages の prewarm と後続処理は必ず走らせる (今朝の修正の趣旨と同じ)。
- `scripts/render_regular_scheduler.py` の self-heal 経路 (`render_detail_pages_selfheal`)
  も同じオプションを使い、**日中に残件を少しずつ埋められる**ようにする。
  self-heal は1日1回ガードがあるので、**残件がある限り再実行できる**よう
  ガード条件を見直す (例: 被覆が十分になるまでは再実行可。ただし
  **実行間隔の下限**を設けて暴走させない)。

### 3. なぜ 900 秒で終わらないのかを調べて記録する

- 192 レース分のタグ生成に 900 秒以上かかっている。**1レースあたり何秒か**を計測し、
  作業ログに記録する。明らかに遅い処理 (N+1 クエリ等) があれば**指摘だけ**して、
  **本タスクでは直さない** (別タスクにする)。安全のためロジック変更は避ける。

## テスト (`tests/` に追加)

- 予算を超えたら、処理済み分を保存したうえで **exit 0** で終わる。
- 既にキャッシュがあるレースはスキップし、無いものが優先される。
- 予算内に全件終わればこれまでどおり完走する (回帰なし)。
- メンテの detail フェーズが「残件あり」でも **失敗にならず**、pages prewarm が走る。
- self-heal が残件のある日に (間隔の下限を守りつつ) 再実行できる。
