# 勝ち筋サーチ Step 24 仕様書 — 有料プラン申込画面と規約同意フロー

作成: 2026-08-17 リン（Claude Code）/ 発注先: Codex
前提: Step 23（708f289）で法定3ページを実装済み。
Stripe Checkout は `src/web/billing.py::billing_checkout`（`POST /billing/checkout`）に実装済み。

## 背景（調査で判明した不足）

現在の `POST /billing/checkout` は **login_required のみ**で、規約同意の確認なしに
Stripe Checkout へリダイレクトする。有料販売では以下が必要:

- 申込前に**料金・課金周期・解約条件・提供内容**を明示した申込画面
- **利用規約とプライバシーポリシーへの同意取得**
- **未同意のまま直接 POST された場合のサーバー側拒否**（クライアント検証だけでは不十分）
- 同意した事実（日時・規約版）の記録

## 実装内容

### 1. 申込画面（`GET /signup/plan`）
- **login_required**（ログイン済みユーザー向け）。
- 表示項目（すべて環境変数由来。未設定はプレースホルダ＋警告）:
  - プラン名 / **価格（税込）** / **課金周期**（月額）/ 次回更新の考え方
  - 提供内容の要約（勝ち筋サーチの利用、**予想の販売ではない**旨）
  - **解約方法と解約時の扱い**（いつまで使えるか、日割り返金の有無）
  - 法定3ページへのリンク（規約 / 特商法 / プライバシー）
- **同意チェックボックス**（1つ、または規約・プライバシーで2つ。実装しやすい方でよい）:
  「利用規約およびプライバシーポリシーに同意します」
- 同意にチェックが入るまで**申込ボタンを無効化**（クライアント側）。
- 既に有料会員の場合は申込ボタンを出さず、**カスタマーポータルへの導線**を表示。

### 2. 同意のサーバー側検証（`billing.py` 最小変更）
- `POST /billing/checkout` に、**同意フラグの検証を追加**する:
  - フォームまたはJSONで `agree_terms`（真）と `terms_version` を受け取る
  - **未同意/欠落なら Stripe を呼ばずに 400** を返す（日本語メッセージ）
  - 価格未設定（`STRIPE_PRICE_ID` 未設定）なら既存どおり 503
- **既存の Stripe 呼び出し処理・成功時リダイレクトは変更しない**。
- 検証ロジックは `signup_bp.py` に置き、`billing.py` からは呼ぶだけにする
  （billing.py の変更を数行に留める）。

### 3. 規約版の管理
- `legal_bp.py` に `TERMS_VERSION`（例 `"2026-08-17"`）を定数として持ち、
  申込画面と検証で共有する。将来規約を改定したら版を上げる運用を結果レポートに記載。

### 4. 同意記録
- **既存のプロファイル/会員テーブルに同意日時・版を保存できるか調査**し、
  可能なら保存する。不可能ならスキーマ変更を提案するに留め、実装しない。
- 最低限、**同意なしでは決済に進めない**ことをサーバー側で担保すれば本ステップの目的は達成。

## テスト
1. `GET /signup/plan` が未ログインでログイン誘導、ログイン済みで200
2. 価格が未設定のとき、申込ボタンが無効＋警告が出る
3. **`POST /billing/checkout` に同意フラグなしで送ると 400**（Stripe を呼ばない）
   → Stripe クライアントをモックし、**呼ばれていないこと**をアサート（最重要）
4. 同意フラグありなら既存フロー（Stripe未設定なら503、設定済みならCheckout生成）に進む
5. 既に有料会員なら申込ボタンではなくポータル導線が出る
6. 法定3ページへのリンクが申込画面に存在する
7. 既存の全テストがグリーン（特に billing 関連の回帰）
