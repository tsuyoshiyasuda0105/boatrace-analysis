## Phase results

### Phase 1: shared cron runtime

- Added `src/db/cron_runtime.py` as the single implementation for:
  `ensure_task_runs_table`, `record_task_run`, `advisory_lock`, and
  `parse_race_close_jst`.
- `record_task_run` now has one lifecycle contract for `running`, `skipped`, `success`,
  and `failure`: a terminal update preserves the attempt's `started_at`, a skipped write
  cannot overwrite a live running row, and an attempt is counted once.
- Postgres keeps the existing migration-owned `task_runs` schema/RLS behavior. Runtime
  table creation remains SQLite-only; Postgres performs only a readiness probe.
- Maintenance, bootstrap, odds, cron run log, and task log delegate to the shared helper.
  Lock names, connection lifetimes, release behavior, and timeout behavior were preserved.
- The regular scheduler lease lock and exhibition scheduler's running-row overlap guard
  were intentionally not migrated, as required by the instruction.

### Phase 2: strict original exhibition finder

- Moved the missing-original-exhibition query and race-close parser to the shared runtime.
- Both regular and exhibition schedulers now use the same strict rule: a race is complete
  only when all six boats have original rows and all lap/turn/straight fields are present.
  Partial rows and all-zero measurements remain retry targets.
- Added unit coverage for complete, partial, and all-zero cases.

### Phase 3: dead-code proof and hold

  service runs with `BOATRACE_REGULAR_LITE=1` and `BOATRACE_DEDICATED_CRONS=1`, and that
  the 07:00, 10:00, 12:00, and 23:35 paths do not call the listed legacy functions.
- Full-accident generation was inspected separately and is not classified as removable.

- Final review found a boundary case where one metric could have six rows while another had

## Deferred design

Lock migration is design-only in this task. A later, separately deployed migration should:

1. Add lock acquisition/skip/hold-time observability without changing ownership semantics.
2. Compare the regular lease and advisory-lock outcomes in production logs before replacing
   either mechanism; do not acquire two exclusive locks in the same execution path.
3. Migrate one scheduler at a time while preserving the current lock name, scope, connection
   lifetime, stale timeout, and skip behavior, followed by a canary period.
4. Keep the exhibition running-row guard until task logging has an attempt identifier that
   can distinguish stale attempts from a currently active attempt.
5. Roll back only the migrated lock adapter if skip counts, overlap counts, or runtimes drift.
