# 勝ち筋サーチ Step 10 仕様書 — 既存ROI手法とのクロスチェック検証

作成: 2026-08-16 リン（Claude Code）/ 発注先: Codex
目的: **既存の本番 ROI 画面の手法（`src/web/app.py` の `ROI_STRATEGIES` とその判定ロジック）を
「正解」の基準とし、新しい勝ち筋サーチの検索エンジンで同じ条件を再現して、
N・的中数・回収率が一致するかを突合する。** 2つの独立実装のクロスチェックで、
どちらかの誤りを炙り出すのが狙い。

## 重要な位置づけ

- これは**検証タスク**であり、**このラウンドでは実装の修正を行わない**（発見と報告に専念）。
- 「ROI画面が正しいと仮定」して差分を出すが、**差分が出た場合にどちらが誤りかは断定しない**。
  差分の原因（条件の再現漏れ / 対象期間の違い / データソースの違い / どちらかのバグ）を
  切り分けて報告すること。**辻褄合わせで数字を合わせにいく行為は厳禁。**

## 絶対的な制約（違反禁止）

1. **プロダクトコードを一切変更しない**。`src/web/`（本番）は読み取りのみ。
   `src/search/`, `src/features/`, `src/kachisuji_web/` も変更禁止。
2. 作ってよいのは: 検証スクリプト（`scripts/crosscheck_roi_strategies.py`）、
   検証テスト（`tests/test_crosscheck_roi_strategies.py`）、
   報告書（`reports/kachisuji_crosscheck_result_20260816.md`）のみ。
3. DB はすべて**読み取り専用**（`mode=ro` + `PRAGMA query_only=ON`）。
   `data/boatrace.db` / `data/kachisuji_search.db` への書込み・DDL 禁止。
   本番 Supabase への接続も禁止（ローカル SQLite のみで完結させる）。
4. 実サーバー起動しっぱなし禁止。ネットワーク・スケジューラ・デプロイ・push 禁止。
5. コミットは main へのローカルコミット1つ。
   メッセージ: `Add ROI strategy cross-check verification (kachisuji step 10)`。

## 手順

### Phase 1: 既存手法の条件を読み解く（調査）
- `src/web/app.py` の `ROI_STRATEGIES` 定義と、各 key の**実際の判定ロジック**
  （条件を評価している関数群）を読み、条件を機械可読な形に書き出す。
- あわせて `adopted_strategies.md` の記載（会場・買い目・条件）も参照して突き合わせる。
  定義とドキュメントが食い違う場合は**コードを正**とし、食い違い自体を報告する。
- 各手法について、勝ち筋サーチの条件JSONで**完全再現できるか**を判定し、3分類する:
  - `A: 完全再現可能` — 全条件を条件JSONで表現できる
  - `B: 部分再現` — 主要条件は表現できるが一部が未対応（未対応項目を明記）
  - `C: 再現不可` — 中核条件が未対応（例: 180日実測ST、展開予測スナップショット、
    壁/軸力スコア、直線・周回タイム順位、T-5オッズ帯が期間外 等）

### Phase 2: 突合（分類 A の手法すべて + B の主要なもの）
- 対象手法ごとに:
  1. 既存ロジックで対象レース集合を算出（`src/web/app.py` の判定関数を**import して再利用**。
     ロジックを写経・再実装しない。import が困難なら理由を報告し、
     最小限の抽出に留めた上でその旨を明記）
  2. 勝ち筋サーチの `search_roi` で同条件・同期間を検索
  3. **N / 的中数 / 回収率 / 対象 race_id 集合**を突合
- 期間は両者で厳密に揃える（既存側が使っている期間定義を採用し、報告書に明記）。
- race_id 集合が食い違う場合は、**差分レースを最大10件サンプリングし、
  各レースでどの条件が食い違ったかを列挙**する（原因究明の材料）。

### Phase 3: 差分の切り分け
差分が出た手法について、原因を以下に分類して報告:
- `condition-gap`: 勝ち筋サーチ側の条件表現が既存条件を再現しきれていない（機能不足）
- `data-source`: 参照データの違い（例: 既存は Supabase / 新は SQLite、
  既存は market_signals キャッシュ / 新は as-of テーブル、集計窓の定義差）
- `kachisuji-bug`: 勝ち筋サーチ側のロジック誤り（疑い）
- `legacy-bug`: 既存 ROI 側のロジック誤り（疑い）
- `period-mismatch`: 対象期間・除外規則の違い
- `unknown`: 切り分け不能（追加調査が必要な点を明記）

**`kachisuji-bug` / `legacy-bug` と判定する場合は、必ず1レース以上の具体例を示し、
生データ（race_results / race_payouts / race_entries）を根拠として提示すること。**

## 成果物: `reports/kachisuji_crosscheck_result_20260816.md`

### 1. サマリ表
| 手法key | ラベル | 再現分類 | 既存N | 新N | 既存的中 | 新的中 | 既存ROI | 新ROI | 判定 | 原因分類 |

- 判定: `一致` / `軽微差`（丸め等、ROI差 <0.5pt かつ N一致）/ `不一致`
- 一致したものも必ず表に載せる（何件検証したかが分かるように）

### 2. 不一致の詳細
不一致ごとに: 差分レース例（race_id・食い違った条件）・原因分類・根拠・推奨対応

### 3. 再現不可（分類C）の一覧
- どの条件が未対応で再現できなかったかを列挙（今後の機能追加の材料）

### 4. 検証範囲の明示
- 検証した手法数 / 分類A・B・Cの内訳 / 突合したレース総数 / 対象期間
- **検証しなかったものは「検証していない」と明記**（推測で埋めない）

## DoD

1. 分類Aの手法を**全件**突合（Bは可能な範囲、Cは一覧化のみ）。
2. 報告書に上記1〜4がそろっている。数字は実行結果に基づく（捏造・推測禁止）。
3. 検証スクリプトが再実行可能（引数で手法key・期間を指定できると望ましい）。
4. プロダクトコード無変更、DB無変更、push なし。
5. 最後に: 検証手法数 / 一致件数 / 不一致件数 / 原因分類の内訳 /
   **`kachisuji-bug` 疑いの有無（最重要）** / コミットハッシュ を出力。

## 注意

- 既存 ROI 側が Supabase 前提で動く場合、ローカル SQLite で同等の判定ができるかを最初に確認すること。
  できない場合は「ローカルで再現可能な手法のみ」に絞り、その旨と対象外手法を明記する
  （接続できないことを理由に検証を捏造しない）。
- 実行時間が長くなる場合は手法数を絞ってよいが、**絞った事実と基準を報告書に明記**すること。
