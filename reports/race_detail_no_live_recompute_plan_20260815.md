## 背景 (2026-08-15 の実障害)

- 会員が「本日のレース」をクリックしてエラー画面 (Render 502) を見た。
- 確認時、web が 502 を返し、その後復帰。**ワーカーが落ちて再起動した**と見られる。
- 本番記録の裏付け:
  - `slow_request` warning: **201件 / 最悪 `/race/20260815-05-04` で 7.8秒**
  - `post_run_detail_cache_targeted` error: `page=0` (詳細ページ再生成が0件)
- 構成: gunicorn **1 worker × 4 threads**。7〜8秒級のリクエストが数本重なると
  スレッドが枯渇し、メモリ・タイムアウトでワーカーが落ちて 502 になる。

**本質**: キャッシュが無い/期限切れのレース詳細を人が開いた瞬間に、
**リクエストスレッド上で重い再計算 (~8-13秒)** が走る。これが 502 の引き金。

## このタスクのゴール

**ユーザーのリクエストが、重い再計算を絶対に引き起こさない**構造にする。
キャッシュが無ければ「準備中」を**即座に**返し、生成は裏 (cron/prewarm) に任せる。

## 絶対ルール

1. **origin/main へ push 禁止** (ローカル main まで)。
2. ROI 戦略ロジック・予測ロジック・DB スキーマ・render.yaml は変更しない
   (ワーカー数の変更は**別タスク**。ここでは触らない)。
3. `.venv/Scripts/python.exe -m pytest tests/ -q` — **702 passed を割らない**。
4. 作業ログ `reports/race_detail_no_live_recompute_work_log_20260815.md`。コミット1〜2個。

## やること

### 1. レース詳細ルートの「ライブ再計算」を止める

`src/web/app.py::race_detail` (~6901) の現行フロー:
1. 今日のページ: 180秒フレッシュキャッシュ → 無ければ stale キャッシュ →
   **無ければライブ再計算 (重い)**
2. 過去のページ: stale キャッシュ → **無ければライブ再計算 (重い)**

これを次のように変える:

- **通常のユーザーリクエスト (人間のブラウザ) では、キャッシュが無い場合に
  重い再計算をしない。** 代わりに「準備中」ページ (HTTP 200、軽量テンプレート、
  `Retry-After` 相当の案内 + 自動リロードの meta refresh 等) を**即座に**返す。
- **例外**: 既存の `EXPENSIVE_RECOMPUTE_TRIGGERS` (render-prewarm / render-cron /
  render-maintenance / render-detail-prewarm / db-maintenance) からのリクエストは
  **従来どおりライブ生成する** (prewarm がキャッシュを埋める経路を壊さない)。
  この判定は既存の仕組み (トリガー判定関数) を読んで再利用すること。新設しない。
- stale キャッシュがあるなら**従来どおり stale を返す** (これは速いので維持)。

**「準備中」ページの要件**:
- 軽量 (DB 問い合わせは最小限、テンプレートは既存の base を流用)。
- 会員に不安を与えない日本語文言 (例:「このレースの詳細を準備しています。
  数十秒後に自動で更新されます」)。**エラー画面に見せない** (500 ではなく 200)。
- 数十秒後に自動リロードする (meta refresh 等、JS 不要の手段が堅い)。

### 2. 「準備中」になったレースを裏で優先的に埋める

準備中を返したとき、そのレースを**次回 prewarm が優先的に生成**できるよう記録する。
- 既存の `page_html_cache` / `system_status` / `task_runs` の仕組みを使い、
  **新テーブルは作らない**。例: `system_status` に軽い記録を残す、または
  既存の prewarm スクリプトが「キャッシュ欠損レース」を自然に拾う実装なら
  **記録は不要** (その場合は作業ログにその旨を書く)。
- **リクエストパス上で重い書き込みをしない** (記録は軽量に。失敗しても無視)。

### 3. 遅いリクエスト記録との整合

既存の slow_request 記録 (閾値超過の記録) はそのまま維持。今回の変更で
「人間のリクエストが8秒かかる」ケース自体が消えるはずなので、
デプロイ後に slow_request が減ることが成功指標になる (作業ログに明記)。

## テスト (`tests/` に追加)

- キャッシュ無し + 通常ユーザー → **重い生成関数が呼ばれず**、準備中ページが 200 で返る。
- キャッシュ無し + prewarm/cron トリガー → **従来どおりライブ生成される**。
- stale キャッシュあり → stale がそのまま返る (従来挙動、回帰しない)。
- フレッシュキャッシュあり (今日) → それが返る (従来挙動)。
- 準備中ページが軽量である (重い依存を呼ばない) ことをモックで確認。
