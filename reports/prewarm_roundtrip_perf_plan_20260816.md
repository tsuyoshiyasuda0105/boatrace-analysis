# 作業指示書: レース詳細プリウォームのDB往復を削減して7倍速くする (Codex CLI 用)

作成: 2026-08-16 / 発注者: リッキー / 検品: リン (Claude)
リポジトリ: `C:\boat_project\boatrace-analysis` (正本のみ)
現行 main: **本番 `17604ab`**。テストは Playwright 未導入で e2e が error になるため
`--ignore=tests/e2e --ignore=tests/round3_e2e` を付けた件数を基準にすること
(直近ベースライン: それで **863 passed** + 既知2件の日付/PKマップ由来 fail は本タスク対象外)。

## 背景 (根本原因は特定済み)

朝のレース詳細プリウォームが遅く、Render の 900秒制限に間に合わず3日連続で
アプリが開けなかった。計測:
- **本番 (Render): 1レースあたり ~3.5秒** (tags は更に遅く、192レースで約20分)
- **ローカル (東京近傍): 1レースあたり ~0.5秒**

**7倍差の原因**:
1. **Render の全 cron は `region: singapore`、Supabase は東京 (ap-northeast-1)**。
   → 1クエリの往復に **~70ms** かかる (ローカルは近いので ~5ms)。
2. プリウォームは **1レースごとに多数のクエリを順次発行** (N+1)。
   往復70ms × 数十クエリ × 192レース = 数十分。

つまり **「per-race のDB往復回数」** が支配的コスト。これを削れば本番でも数分で終わる。

## ゴール

**プリウォーム全体のDB往復回数を大幅に削減**し、192レースの tags+pages 生成が
**Render (シンガポール↔東京) でも 900秒に十分収まる**ようにする。
**出力 (キャッシュ内容) は1バイトも変えない** (純粋な性能改善)。

## 絶対ルール

1. **origin/main へ push 禁止** (ローカル main まで)。
2. **ROI 戦略・予測ロジック・DB スキーマ・render.yaml は変更しない。**
   region 変更 (インフラ) はこのタスクでは行わない (発注者へ提言としてのみ記す)。
3. **挙動不変**: 生成される tag/page キャッシュの内容が、変更前と **バイト単位で一致**
   すること。代表レースで before/after を比較する特性化テストを付ける。
4. テスト: `.venv/Scripts/python.exe -m pytest tests/ -q --ignore=tests/e2e --ignore=tests/round3_e2e`
   がベースライン (863 passed) を割らない + 新規 green。
5. 作業ログ `reports/prewarm_roundtrip_perf_work_log_20260816.md`。コミット2〜4個。

## やること

### 1. まず「1レースあたりのDB往復回数」を計測する (改善の土台)

- `scripts/prewarm_race_detail_tags.py` → `_build_race_detail_tag_snapshot(race_id)`
  (app.py ~5021 付近から呼ばれる本体) と、
  `scripts/prewarm_race_detail_pages.py` の per-race 経路について、
  **1レース処理で `conn.execute(...)` が何回呼ばれるか**を計測する
  (テスト用の counting connection ラッパ、または SQL ロガーで数える)。
- 代表 1レースの往復回数を作業ログに記録 (before)。これが7倍差の実体。

### 2. 往復を減らす (本丸)

以下を**挙動を変えずに**適用する。効果の大きいものから:

- **接続の使い回し**: プリウォームのループが**レースごとに `db_connect()` を開き直して
  いる**なら、**ループ全体で1本の接続を共有**する (per-open のプール取得・
  `configure` の SET 文などの往復を消す)。per-race 関数に `conn` を渡せるよう
  引数を追加し、渡されたらそれを使う (既存の `owns_connection` パターンに倣う)。
- **クロスレース一括プリフェッチ**: 全レース (192件) で共通に引くデータ
  (モーター成績・選手情報・会場マスタ・番組・予測など) を、**ループ前に数本の
  一括クエリでまとめて取得**し、per-race 処理へ辞書で渡す。per-race の個別 SELECT を
  この辞書参照に置き換える。**1レースN往復 → 全体で数往復**へ。
- **per-race 内の重複クエリ統合**: 同じ race_id で複数回引いている箇所を1回にまとめる。

**重要**: どのデータをどうまとめても、**最終的にキャッシュへ書く内容は不変**であること。
まとめて取ったデータが個別取得と一致することを保証する (欠損時の既定値も同じに)。

### 3. 計測 (after) と検証

- 改善後の per-race 往復回数を記録 (after)。**目標: per-race の往復を大幅減**
  (例: 数十 → 数回)。
- ローカルで 10〜20 レースを実際にプリウォームし、**1レースあたり秒数**の before/after を
  作業ログに記録 (ローカルは低レイテンシなので差は小さく出るが、往復回数の削減が
  本番での短縮に直結することを明記)。

### 4. region ミスマッチの提言 (コードは変えない)

作業ログに「Render cron=singapore / Supabase=東京 で ~70ms/往復。往復削減に加え、
**crons を東京リージョンへ移せば更に短縮**できる (ただし Render のリージョン変更は
サービス再作成が必要なインフラ作業なので発注者判断)」と**提言のみ**記す。
render.yaml は変更しない。

## テスト (`tests/` に追加)

- **バイト一致の特性化**: 代表 race_id で、改善前の per-race ビルド結果と
  改善後の結果が **完全一致** (fake/固定フィクスチャで DB を与え、出力 dict/HTML を比較)。
- **一括プリフェッチ = 個別取得**: まとめ取得したデータが、従来の個別取得と同じ値
  (欠損レース・値なしの既定も含む) を返す。
- **接続共有**: ループが接続を1本で回す経路と、従来どおり per-race で開く経路の
  両方で結果が一致 (回帰なし)。
- 往復カウントのテスト (counting connection で、改善後の per-race 呼び出し回数が
  期待上限以下)。
